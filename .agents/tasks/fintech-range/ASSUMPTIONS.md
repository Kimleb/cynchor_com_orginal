# Assumptions: container backend
(carried over from setup step)
- `docker` CLI 29.10.0 talks to **rootless Podman 5.4.2** (Docker-compatible API, reports itself as "Podman Engine"). `DOCKER_HOST=unix:///run/user/1000/podman/podman.sock` is set. `/var/run/docker.sock` also exists (root:docker, not usable by this user).
- Docker CLI reports API 1.41 (downgraded from 1.57); Podman API 5.4.2, min 4.0.0.
- Runtime crun, network backend netavark, storage overlay (extfs, no native shifting), cgroup v2 with systemd driver, security: apparmor, seccomp default, rootless.
- Rootless caveats to design for:
  - Bind-mounted files appear owned by uid mapping (user namespace). Avoid bind mounts entirely for the range target (spec requires no host mounts in the container anyway); copy source in at build/run time instead.
  - Networking uses netavark; `--internal` networks must be verified with an isolation self-test, including whether DNS between containers on an internal network still resolves container names (needed for proxy->target routing).
  - `--cap-drop=ALL`, `--read-only` and `--tmpfs` are supported; tmpfs mount options (noexec/nosuid/size) must be set explicitly since defaults may differ from Docker.
  - Resource limits (`--memory`, `--cpus`, `--pids-limit`) need cgroup v2 controller delegation to the user; verified empirically in FEAT-002 before being relied on, with a documented fallback (log a warning, don't crash the orchestrator) if a given limit silently has no effect under rootless Podman.
  - Docker-only features (swarm, some `docker events` fields, legacy links) are absent — avoid them.
- Host Node is v20.19.2 and lacks `node:sqlite` (needs Node >= 22.5). User-space Node v22.23.5 lives at `.tools/node22` (git-excluded via `.git/info/exclude`); every command in this task must put `.tools/node22/bin` first on PATH.
- `docker.io/library/node:22-alpine` is already pulled locally (171MB) — used as the range-target container's base image.
- `npm run build` creates an untracked `local.sqlite` in the repo root; not git-ignored, left in place, never committed.

# New decisions for the Fintech Range feature (this task)

- **DB layer / migrations**: the app has no migration framework. `src/lib/db.ts` uses Node's built-in `node:sqlite` (`DatabaseSync`) with an idempotent `initSchema()` run on first `getDb()` call: `CREATE TABLE IF NOT EXISTS` for new tables, and defensive `try { db.exec('ALTER TABLE ... ADD COLUMN ...') } catch {}` for new columns on existing tables. New range tables (`range_matches`, `range_events`, `range_exploits`, `range_queue` or similar) follow the exact same pattern: added inside `initSchema()`, each wrapped so re-running is a no-op. No new ORM, no new migration tool — consistent with how `audit_logs`/`users`/`access_requests` columns were evolved in place.
- **RBAC / admin**: there is no generic `role`-string RBAC. Operator/admin power is the single boolean `users.is_operator` column, checked directly in route handlers (`if (!user || !user.is_operator)`), e.g. `src/app/api/admin/route.ts`. The new admin **kill switch** route reuses this exact check — no new role, no new table.
- **audit_logs / match_sessions**: `audit_logs` is append-only (DB triggers block UPDATE/DELETE) and is written via `recordAuditLog({ userId, action, details, ip })` in `src/lib/db.ts`; all new range events (container start/stop, exploit landed, patch applied, kill-switch use) are recorded through this same helper — no second logging path. `match_sessions` already exists for the simulated matchmaking flow (`red_team_id`, `blue_team_id`, `mode`, `status`); the real range match reuses this table rather than inventing a parallel one, adding only the columns the real match needs (vault balance, timestamps, target container id) via the same defensive `ALTER TABLE` pattern. A new `range_target_matches` table stores range-specific fields that don't belong on the generic `match_sessions` row (container id, network id, started_at, ended_at, vault_balance_cents, winner) instead of widening `match_sessions` with range-only columns, keeping the existing simulated-match code paths (tests `matchLifecycle.test.ts`, `endMatch`, `endStaleMatches`) untouched and still valid for the old simulated flow.
- **Auth guard reuse without touching login/sessions/middleware/guards**: every protected page in this app calls `await requireUser(...)` from `src/lib/guards.ts` inside a server-only `layout.tsx` (see `src/app/demo/matchmaking/layout.tsx`, `src/app/admin/layout.tsx` which inlines the same `getCurrentUser()` + `is_operator` check instead of using `requireUser`), and every protected API route calls `getCurrentUser()` directly at the top of the handler (see `src/app/api/matchmaking/route.ts`, `src/app/api/lab/route.ts`, `src/app/api/admin/route.ts`). New range pages under `src/app/range/**` get a new `src/app/range/layout.tsx` that calls `await requireUser({ profile: true })` — an *additive* new file, zero edits to `guards.ts`, `session.ts`, or `middleware.ts`. New range API routes under `src/app/api/range/**` call `getCurrentUser()` directly at the top of each handler, exactly like the existing API routes. The kill-switch route additionally checks `is_operator`, exactly like `src/app/api/admin/route.ts`. `middleware.ts`'s CSRF/CSP logic is already path-agnostic (`pathname.startsWith('/api/')`) so new API routes are covered by it automatically with no edit needed.
- **Docker access — raw Engine API over the socket, not dockerode**: verified empirically that Node's built-in `http` module can talk to the Podman/Docker socket directly (`http.get({ socketPath, path: '/v1.41/_ping' })` returned `200 OK` against `/run/user/1000/podman/podman.sock`). `dockerode` is not in `package.json` and is unnecessary. The orchestrator (`src/lib/range-runtime/dockerClient.ts`) is a small wrapper around Node's `http`/`https` request functions that targets either a Unix socket (`socketPath`) or a remote TCP host (`host`/`port`, optionally TLS) depending on config — `DOCKER_HOST` env var (`unix:///...` or `tcp://host:port`) is parsed once at module load, giving "supports a remote Docker host via config" for free without adding a dependency. All Docker calls (create/start/stop/remove container, create/remove network, stats, logs) go through this one client; nothing else in the app imports it.
- **Live patching**: Blue's patch console writes only into a tmpfs mounted inside the running target container (`/app` is copied from the read-only image layer into a `--tmpfs /app:exec,size=64m` at container start via an entrypoint script baked into the target image, not a host bind mount), then the target's own small process supervisor (a tiny loop in the entrypoint) restarts the Express process. The orchestrator relays the patch's new file content through `docker exec`-equivalent (`POST /containers/{id}/exec` + `start`) rather than a bind mount, keeping "no host mounts inside the container" true.
- **Proxy reach**: the orchestrator attaches a per-match reverse-proxy path on the Next.js side (an API route that forwards HTTP requests to the target container's internal IP, resolved via Docker network inspect) rather than exposing a published port — satisfies "no published ports, reachable only through the platform's reverse proxy" and "never a direct container IP" for players, since players only ever call the Next.js route.
- **Scoring**: a scorer module polls the exploit-proof test functions (compiled to plain async functions importable from both `tests/range-target/*.test.ts` and the scorer, not re-implemented) against the live target's proxied URL on an interval (e.g. every 5s), plus a `/health` check; a result only counts if the health check passed in that interval (down app ≠ blocked).
- **Realtime**: Server-Sent Events (`text/event-stream` from a Next.js Route Handler using a `ReadableStream`), not WebSockets — there is zero existing WebSocket/SSE code in the repo to be consistent with either way, and Next.js Route Handlers support SSE with a plain `ReadableStream` response without extra infrastructure (no custom server needed), whereas WebSockets would require a custom server or an external service. Matches the pre-made decision "SSE preferred over WebSockets unless the repo makes WebSockets clearly easier" — it doesn't.
- **Target app stack**: `/range-target/` is a standalone Express + `node:sqlite` (or `better-sqlite3`-free, using the same built-in `node:sqlite` already proven to work in this Node 22 environment) app, server-rendered with plain EJS/HTML strings (no React/Next build step), run inside the Node 22-alpine base image already pulled locally.
- **No email/PII**: all new tables key players by `user_id`/`username` only (joining back to the existing `users.name` for display, never `users.email`); the After Action Report and leaderboards render `name`/username, never email.
- **FEAT-002 limits verified**: under rootless Podman the memory (256MiB), pids (128) and cpu (0.5) limits were measured effective via cgroup files inside the container; the orchestrator still compares and logs RANGE_LIMIT_WARNING if a future host differs. tmpfs uses mode=1777 (uid= unsupported); capability drop verified from /proc/self/status.

## range-fixes decisions
- **Leaderboard room/level:** the range has no level concept. Room = match session id (`?matchId=`), level = exploit id from `EXPLOIT_IDS` (`?exploit=`). Both optional, combinable, validated (400 on bad values). An exploit filter keeps only matches where that exploit landed and counts only those `RANGE_EXPLOIT_LANDED` rows (patches shown as 0).
- **Reaper ENDS, never resumes:** scorer and orchestrator state (timers, log cursor, per-exploit state) is in-process, so a restarted server cannot resume a match faithfully. Active rows not in the live map, or past `timeout_at`, are destroyed and ended (TIMEOUT, or KILLED "reaped: server restarted"); the scorer's reconcile then frees the teams and writes the After Action Report. Labelled Docker objects not owned by an active row are removed. Rows younger than 30 s are skipped so the reaper cannot race `startMatch`.
- **Vault persistence:** a second tmpfs `/data` holds `RANGE_DB_PATH=/data/range.sqlite`, so a patch restart reopens the same DB (`seed()` is guarded). tmpfs is RAM-only, container-local, no host mount, no new egress; caps, read-only rootfs, internal network and limits are unchanged. Because Blue can still rewrite `db.js`, the scorer keeps a monotonic vault floor in `range_target_matches.vault_balance_cents`: a read above the floor is clamped and logged as `RANGE_VAULT_RESET_DETECTED`; reports read the floor.
